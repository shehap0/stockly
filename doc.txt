# 1. PROJECT OVERVIEW

Build a centralized Auto Parts Inventory and Sales Management System.

The business has three physical branches.

Each branch:
- Has its own employees.
- Has its own physical inventory.
- Can sell products.
- Can add newly purchased products manually.
- Can manage its own stock quantities.
- Can view the availability of products in other branches.

All branches share one central product catalog and one centralized database.

The system must allow the owner to manage the entire business from one application.

## Core business principles

1. One company.
2. Three branches.
3. One shared product catalog.
4. Separate inventory quantities for each branch.
5. Centralized database.
6. Real-time inventory synchronization.
7. No inventory transfers between branches.
8. No supplier management.
9. No purchase-order management.
10. No complicated accounting system.
11. No payment gateway integration.
12. Manual product creation and manual stock additions.
13. Simple cash and card payment recording.

This is a small business application, NOT an enterprise ERP platform.

Avoid unnecessary complexity.

# 5. INVENTORY BUSINESS LOGIC

Implement inventory operations as secure, atomic database transactions.

## 5.1 Product creation

When a product is created:
- Validate required fields.
- Validate optional attributes.
- Save the product in the shared catalog.
- Do not automatically assign stock to every branch.
- Allow stock to be added separately.

## 5.2 Adding stock

A branch employee selects:

- Product.
- Branch (restricted to authorized branches).
- Quantity.
- Purchase cost (optional).
- Reason (optional).

The server:
1. Validates the user and branch permissions.
2. Validates the product.
3. Validates the quantity.
4. Creates or updates the branch inventory record.
5. Creates an inventory movement.
6. Commits the operation atomically.

This is how the business manually records products purchased locally.

Do not create supplier or purchase-order entities.

## 5.3 Stock adjustments

Allow authorized users to correct inventory quantities.

Examples:
- Physical count correction.
- Damaged product.
- Lost product.
- Incorrect previous entry.

Every adjustment must include:
- Product.
- Branch.
- Quantity change or corrected quantity.
- Reason.
- User.
- Timestamp.

Negative inventory is forbidden.

## 5.4 Inventory queries

Implement queries for:

- Stock in a particular branch.
- Stock across all branches.
- Total company stock.
- Products with zero stock.
- Low-stock products.
- Products by category.
- Products compatible with a selected vehicle, where compatibility information exists.
- Search by product name, SKU, barcode, OEM number, and optional vehicle attributes.

The search must work even when optional attributes are missing.

## 5.5 Low-stock alerts

Support a configurable threshold for each product at each branch.

For example:

Product: Oil Filter
Branch 1 quantity: 2
Low-stock threshold: 5

This product should appear in the low-stock list for Branch 1.

A branch can have a different threshold for the same product.

# 6. SALES MANAGEMENT

Build a simple sales recording system, not a sophisticated retail POS platform.

## 6.1 Sale workflow

1. Employee opens the sales section.
2. Employee selects products.
3. Employee enters quantities.
4. System retrieves current selling prices.
5. System calculates subtotal.
6. Employee optionally applies a discount.
7. Employee selects CASH or CARD.
8. Employee confirms the sale.
9. Server validates and records the transaction.
10. Inventory decreases automatically.
11. Inventory movement records are created.
12. Sale appears in sales history.
13. Other branches receive updated stock information.

## 6.2 Discounts

Support:

- Fixed amount discount.
- Percentage discount.

Requirements:
- Discounts cannot exceed the sale subtotal.
- Discounts cannot create negative totals.
- Define clear rounding rules.
- Record the original subtotal.
- Record the discount amount.
- Record the final total.
- Restrict discount permissions where appropriate.

## 6.3 Transaction safety

This is critical.

A sale must be processed as one atomic database transaction.

The following must happen together:

- Validate stock availability.
- Deduct quantities.
- Insert sale.
- Insert sale items.
- Insert inventory movement records.

If any operation fails, everything must roll back.

Never deduct inventory before confirming that the entire transaction can succeed.

Prevent race conditions.

Example:

Branch 1 has one brake pad.

Two employees attempt to sell the last unit simultaneously.

Only one sale may succeed.

Use appropriate PostgreSQL row locking or equivalent transactional mechanisms.

Use an idempotency mechanism to prevent duplicate sales when a user retries after a network timeout.

## 6.4 Sale history

Support:
- Search by sale number.
- Search by date.
- Filter by branch.
- Filter by payment method.
- Filter by employee.
- View individual sale details.
- View products sold.
- View discounts.
- View final payment amount.

Do not allow historical sales to be silently edited.

For voids or returns, create traceable compensating inventory movements and preserve the original transaction.

# 7. REAL-TIME SYNCHRONIZATION

Use Supabase Realtime where appropriate.

All branches must receive relevant inventory updates without refreshing the entire application.

Example:

1. Branch 1 has 10 oil filters.
2. Employee sells 2.
3. The server updates inventory to 8.
4. The server commits the transaction.
5. Branch 2 receives the database change.
6. Branch 3 receives the database change.
7. Both branches update their displayed availability.

Important rules:

- PostgreSQL is the source of truth.
- Realtime is a notification mechanism, not the primary storage mechanism.
- Never trust a realtime event as proof that a transaction succeeded.
- Refresh or reconcile the relevant data from PostgreSQL when necessary.
- Avoid subscribing every user to unnecessary data.
- Restrict subscriptions to appropriate records and authorized data.
- Handle reconnecting clients.
- Handle missed realtime events.
- Use TanStack Query invalidation or equivalent cache reconciliation.

A temporary realtime disconnection must not corrupt inventory.

## Internet failure

Initially, use an ONLINE-ONLY architecture.

If the connection is unavailable:
- Do not pretend that a sale was successfully synchronized.
- Show an appropriate connection error.
- Do not silently queue sales without implementing proper offline transaction handling.
- Allow retrying failed requests safely.
- Use idempotency to prevent duplicate operations.

Offline-first functionality is explicitly outside the initial scope.
